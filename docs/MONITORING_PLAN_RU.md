# План мониторинга, алертов и реакции

## Что уже реализовано

`app/metrics.py` экспортирует **агрегированные** Prometheus-метрики на эндпоинте `/metrics`:

| Метрика | Что считает | Как используется |
|---|---|---|
| `up{job="toxicity-api"}` | Доступность сервиса для сбора метрик: 1 — отвечает, 0 — нет | Сигнал «сервис жив»: выводится на дашборд доступности; падение в 0 означает, что API не отвечает |
| `toxicity_http_requests_total{route,status}` | Число ответов API с разбивкой по маршруту и HTTP-коду | Два вывода: нагрузка (сколько запросов в секунду приходит) и здоровье (какая доля ответов — ошибки 5xx) |
| `toxicity_http_request_duration_seconds{route}` | Длительность обработки HTTP-запросов (гистограмма) | Показывает, как быстро пользователь получает ответ целиком; рост p95 здесь при нормальном времени модели указывает на проблему вне инференса — БД, валидация, нагрузка |
| `toxicity_inference_duration_seconds{source}` | Время работы модели на одно предсказание, по источникам `telegram`/`api` (гистограмма) | Изолирует скорость самой модели; рост p95 здесь при нормальном общем времени ответа означает, что узкое место — инференс |
| `toxicity_predictions_total{source,predicted_class}` | Число успешных классификаций по источнику и предсказанному классу | Доли классов в потоке со временем: резкий сдвиг намекает, что изменилась аудитория или тематика сообщений — повод проверить разметку и качество, **косвенный признак drift, не метрика точности** |

С каких метриких и по каким условиям построены алерты — в разделе ниже.

Конфигурации: `monitoring/prometheus/prometheus.yml`, `monitoring/prometheus/alerts.yml`, `monitoring/grafana/dashboards/toxicity-overview.json`. Интервал сбора — 15 сек. Prometheus обращается к `api:8000/metrics` по **внутренней Docker-сети** независимо от внешнего порта хоста.

## Реально заданные алерты (Prometheus rules)

| Алерт | Когда срабатывает | Что делать |
|---|---|---|
| `ToxicityAPIDown` (critical) | API не отвечает на сбор метрик непрерывно **2 минуты** | Проверить контейнер (`docker compose ps`), здоровье (`/health/ready`), логи API и состояние БД; восстановить сервис, при необходимости — откатить версию |
| `ToxicityHighPredictionErrorRate` (warning) | Больше **5%** ответов `/predict` — ошибки 5xx, по данным последних **5 минут**, и так держится **10 минут** | Разобрать ошибки в логах, проверить БД и файл модели; при подтверждении проблемы — откатить версию |
| `ToxicityHighPredictionLatency` (warning) | p95 времени работы модели больше **1 секунды** (по данным последних **5 минут**), держится **10 минут** | Проверить CPU/RAM, размер входных текстов и рост нагрузки; при необходимости ограничить трафик или масштабироваться |

**Важно:** правила уже настроены в Prometheus, однако **канал доставки уведомлений (Alertmanager/email/Telegram) не подключён и не проверен**. Алерты видны только в интерфейсе Prometheus → Alerts и на дашборде Grafana; автоматическая отправка уведомлений не реализована.

## Данные/модель: план контроля дрейфа и качества

1. **Распределение прогнозов и источников**: сравнивать доли `neutral/offensive/toxic` за день/неделю с согласованным «здоровым» периодом. Для малой выборки (как после 20 тестовых запросов) сигнал неинформативен. Не считать нормой доли обучающего набора: рабочий поток может отличаться.
2. **Длина, язык и формат входных текстов**: в текущем API сбор гистограммы длины и детектора языка **не реализован**. На следующем этапе добавить *агрегированные* гистограммы (без сырого текста, IP, идентификаторов), сравнивать медиану/p95 с эталонным периодом.
3. **Доверие модели**: периодически измерять распределение max probability/confidence по источникам из защищённой БД (не экспортировать пользовательские тексты или IDs). Изменение уверенности — сигнал к расследованию, не доказательство ошибки.
4. **Качество по ground truth**: раз в неделю/месяц проводить ручную разметку репрезентативной случайной выборки (с согласованными правами на данные), рассчитывать macro-F1, `recall toxic`, матрицу ошибок и сравнивать с baseline и предыдущими периодами. До появления меток `true_class` **production-F1 недоступен**.

**Предлагаемое условие для ручного/будущего алерта на дрейф (пока не реализовано):** при минимум **200** новых предсказаниях за **24 часа** доля любого класса отличается от эталонной более чем на **15 процентных пунктов** два дня подряд. Действие — проверить источник трафика, собрать размеченные примеры и сравнить качество. Это **начальный порог для калибровки**, не универсальное правило: его нельзя применять без валидации сезонности и ложных срабатываний. Критические автоматические решения не принимаются.

**Предлагаемое условие для ручной проверки ухудшения модели:** при наличии минимум **100** размеченных новых примеров, если недельный recall(`toxic`) ниже **0,80**, инициировать аудит разметки и сравнение с эталоном. При малом числе примеров toxic оценка статистически нестабильна — нужна проверка доверительных интервалов. Это план, а не действующий Prometheus-алерт.

## Результаты локального мониторинга

На сохранённых снимках экрана Prometheus Target `toxicity-api` со статусом **UP (1/1)** и Grafana: `API availability=1`, показаны requests/sec, p95 inference около **0,00957 с** на тестовых запросах, распределение класса `neutral`. Это подтверждает, что базовые метрики доходят до Grafana, но **не** подтверждает настройку уведомлений, полноценный drift detection или промышленную производительность.
